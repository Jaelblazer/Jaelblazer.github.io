01

Investigate the TCP/IP and OSI Models in Action

Cyber Shujaa · Cisco Packet Tracer
Problem Statement

Show how data actually moves through the OSI and TCP/IP models by following real traffic across a simulated network, rather than just memorising the layers.

Tools Used
Cisco Packet TracerSimulation modePDU inspection
Approach
  • Generated traffic between hosts in Packet Tracer's simulation mode and stepped through each packet.
  • Opened the PDU details at each device to map fields and headers to the OSI and TCP/IP layers.
  • Observed encapsulation and de-encapsulation as frames moved between the hosts, switch and router.
  • Recorded findings with screenshots and answered the lab questions in a written report.
Key Lessons Learned

Seeing a packet at every hop makes the layered models concrete: each layer adds its own header, and knowing which layer a field belongs to is what lets you troubleshootand later analyse traffic quickly.

02

Use Wireshark to View Network Traffic

Cyber Shujaa · Wireshark on Arch Linux
Problem Statement

Capture live network traffic and identify what different protocols look like on the wire, including the ICMP exchange between two devices.

Tools Used
WiresharkArch Linuxping / ICMPCapture filters
Approach
  • The lab assumed Windows, so I adapted it to Arch Linux and set up Wireshark with the right capture permissions.
  • Without a second team member to ping, I used the router as a stand-in peer to generate local ICMP traffic.
  • Captured the exchange, filtered to the relevant protocol, and inspected the packet details and headers.
Key Lessons Learned

Labs rarely match your environment exactly adapting the setup taught me more than following steps would have. It also reinforced that filters are essential: a busy interface is unreadable until you narrow it to the traffic you care about.

Introduction to Network Traffic Analysis

Hack The Box Academy · Badge: “Lurk in the Packets”
Problem Statement

Learn to analyse network traffic the way a defender does — capturing, filtering and interpreting packets to understand what is happening on a network.

Tools Used
tcpdumpWiresharkHTB Academy
Approach

04

Build a Switch and Router Network

Cyber Shujaa · Cloud and Network Security · Cisco Packet Tracer
Problem Statement

Build a dual-stack network in which one router (R1) connects two subnets PC-B on one interface, and PC-A behind a switch (S1) on the other then secure the devices and prove end-to-end connectivity over both IPv4 and IPv6.

Tools Used
Cisco Packet TracerCisco 1941 routerCisco 2960-24TT switchCisco IOS CLIpingshow commands
Approach
  • Cabled the router, switch and two PCs with copper straight-through links to match the topology, and confirmed both devices booted clean.
  • Assigned static IPv4 and IPv6 addresses to both PCs, then confirmed the first pings failed because no router interface existed yet to route between the two subnets.
  • Configured R1's two Gigabit interfaces with IPv4 and IPv6 addresses, descriptions and no shutdown; hardened it with an enable secret, console and VTY passwords, service password-encryption and a MOTD banner.
  • Configured S1 with a hostname, DNS lookup disabled, a VLAN 1 management address and a default gateway, then saved the running config to NVRAM.
  • Verified with pings across both protocols and inspected the result with show ip route, show ipv6 route, show ip interface and the brief summaries.
Challenges Faced & How I Resolved Them
  • Interface names didn't match the lab. The lab text assumed a Cisco 4221 (G0/0/0, G0/0/1) but I used a 1941 (G0/0, G0/1). I checked the router's modules in the Physical tab and mapped each interface to its equivalent.
  • IPv6 address syntax needed a second attempt. I corrected the command format and re-applied the addressing.
  • VTY lines were configured incorrectly at first. I reviewed the line configuration and rebuilt it properly with login enabled.
  • A missing hyphen broke the password-encryption command. The correct command is service password-encryption; reading the CLI error carefully exposed the typo.
  • IPv6 pings failed with 100% loss. Each interface had a valid IPv6 address, but the router wasn't forwarding until I enabled ipv6 unicast-routing; the same ping then succeeded with 0% loss.
Key Lessons Learned
  • An address on an interface isn't enough: a router only routes IPv6 once ipv6 unicast-routing is enabled.
  • The first ping often times out because the router must complete ARP resolution first a timeout isn't always a fault.
  • Hardware differs from lab guides (interface naming varies by router model), so I adapt commands to what the device actually presents rather than copying them verbatim.
  • Each verification step traced back to a specific piece of configuration being present or missing, which made troubleshooting systematic.
